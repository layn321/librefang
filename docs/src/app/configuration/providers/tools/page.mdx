# Developer Tool Providers

This page covers providers that integrate through local assistant tooling or CLI runtimes instead of a standard remote LLM API. They are useful when LibreFang agents need to reuse an existing coding or terminal-assistant stack.

## Included Providers

- Claude Code
- GitHub Copilot
- ChatGPT (Session Token)
- Kimi Coding
- Aider
- Claude Code CLI
- Codex CLI
- Gemini CLI
- Qwen Code
- Claude Code and Codex over ACP

## CLI logins as first-class default providers

When you have not set a provider API key but **do** have a working CLI login (`claude`, `codex`, `gemini`, `qwen` available on `PATH` and authenticated), LibreFang will pick the CLI provider as the default model for new agents. The detection runs at startup and is rechecked when the daemon refreshes provider availability.

Detection priority (in order, first match wins):

1. `claude-code` — `claude` binary on `PATH`, `claude auth status` reports an active session.
2. `codex-cli` — `codex` binary on `PATH`, with `OPENAI_API_KEY` (which the Codex CLI itself needs) set.
3. `gemini-cli` — `gemini` binary on `PATH`, authenticated via `gemini auth login`.
4. `qwen-code` — `qwen` binary on `PATH`, authenticated.

This behaviour replaced the previous "fallback when API providers fail" heuristic — CLI providers are now treated like any other remote provider. To explicitly override the auto-pick, set `[default_model] provider = "anthropic"` (or whichever) in `config.toml`.

## GitHub Copilot

| | |
|---|---|
| **Display Name** | GitHub Copilot |
| **Driver** | OpenAI-compatible (via Copilot token exchange) |
| **Env Var** | `GITHUB_TOKEN` |
| **Base URL** | `https://api.githubcopilot.com` |
| **Key Required** | Yes (GitHub PAT or OAuth token) |
| **Free Tier** | Included with GitHub Copilot subscription |
| **Auth** | OAuth PKCE flow; exchanges GitHub PAT for short-lived Copilot API token |
| **Models** | GitHub Copilot-hosted models (GPT-4o, Claude, etc.) |

**Setup:**
1. Subscribe to [GitHub Copilot](https://github.com/features/copilot)
2. Create a Personal Access Token with `copilot` scope
3. `export GITHUB_TOKEN="ghp_..."`

**Notes:** The Copilot driver handles OAuth PKCE token exchange automatically — it obtains a short-lived Copilot API token from `https://api.github.com/copilot_internal/v2/token` and caches it with auto-refresh. The Copilot API uses OpenAI-compatible chat completions format. Tokens are refreshed 5 minutes before expiry.

## ChatGPT (Session Token)

| | |
|---|---|
| **Display Name** | ChatGPT |
| **Provider ID** | `chatgpt` |
| **Driver** | Native ChatGPT (Responses API) |
| **Env Var** | `CHATGPT_SESSION_TOKEN` (primary), `CHATGPT_REFRESH_TOKEN` (optional) |
| **Base URL** | `https://chatgpt.com/backend-api` |
| **Key Required** | Yes (browser session token) |
| **Free Tier** | Subscription-based (ChatGPT Plus / Pro / Team / Enterprise) |
| **Auth** | Session token + bearer; OAuth-style refresh with ~7-day TTL |

**Setup:**
1. Run `librefang auth chatgpt` (browser-based OAuth flow). The CLI captures the session token and caches it.
2. The token auto-refreshes 1 hour before expiry; no manual rotation needed.

**Minimal `config.toml`:**

```toml
[default_model]
provider = "chatgpt"
model = "gpt-4o"
```

**Notes:** Uses the proprietary Responses API rather than `/v1/chat/completions`. This lets agents reuse a paid ChatGPT subscription without a separate OpenAI API key. **Tools and vision supported.** Embeddings are not available via this driver — use OpenAI hosted instead.

## Aider

| | |
|---|---|
| **Display Name** | Aider |
| **Type** | **CLI Provider** |
| **Driver** | Subprocess (CLI) |
| **Env Var** | None (uses its own provider env vars) |
| **Binary** | `aider` (must be on PATH) |
| **Key Required** | No (uses Aider's own auth) |
| **Free Tier** | Depends on Aider's configured backend |

**Setup:**
1. Install Aider: `pip install aider-install && aider-install`
2. Configure Aider's LLM provider via its own env vars (e.g. `OPENAI_API_KEY`)
3. No additional LibreFang configuration needed

**Notes:** CLI Provider — LibreFang spawns the `aider` binary as a subprocess in non-interactive mode (`--message`). Aider handles its own LLM provider authentication via standard environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, etc.). Aider's `--yes-always`, `--no-auto-commits`, and `--no-git` flags are applied automatically. Use `AIDER_CLI_PATH` to override the binary path.

## Claude Code CLI

| | |
|---|---|
| **Display Name** | Claude Code CLI |
| **Type** | **CLI Provider** |
| **Driver** | Subprocess (CLI) |
| **Env Var** | None (uses its own OAuth session) |
| **Binary** | `claude` (must be on PATH) |
| **Key Required** | No (uses Claude Code's own session auth) |
| **Free Tier** | Depends on Claude Code subscription |

**Setup:**
1. Install Claude Code: `npm install -g @anthropic-ai/claude-code`
2. Authenticate: `claude auth login`
3. No additional LibreFang configuration needed

**Notes:** CLI Provider — LibreFang spawns the `claude` binary as a subprocess in print mode (`-p`). The driver strips other providers' API keys from the subprocess environment to prevent leakage. Active subprocess PIDs are tracked and message timeouts (default 5 minutes) prevent hung processes from blocking agents. Vision input is supported via base64-encoded images.

## Claude Code and Codex over ACP

| | |
|---|---|
| **Provider IDs** | `claude-code-acp`, `codex-acp` (aliases `claude_code_acp`, `codex_acp`) |
| **Type** | **CLI Provider** (ACP client) |
| **Driver** | `acp_client`: LibreFang is the [Agent Client Protocol](https://agentclientprotocol.com) client |
| **Adapter** | `claude-agent-acp` / `codex-acp` (must be on PATH, or configured) |
| **Key Required** | No (the CLI uses its own login, or the gateway variables below) |

LibreFang spawns an ACP adapter, which drives the real CLI as a long-lived agent, and talks to it over ACP on stdio: `initialize`, then `session/new` (working directory plus the LibreFang MCP bridge when the agent has tools), then `session/prompt`. `session/update` chunks stream back as text, thinking and tool-phase events; tool calls run inside the agent and are never handed to the LibreFang tool loop. No print or one-shot CLI mode is used.

**Setup:**
1. Install the CLI you want and log in (`claude`, or `codex`).
2. Install the adapter:
   - Claude Code: `npm install -g @agentclientprotocol/claude-agent-acp` (formerly `@zed-industries/claude-code-acp`; its `claude-code-acp` binary also works if you point the path at it).
   - Codex: `npm install -g @agentclientprotocol/codex-acp`.
3. Set `[default_model] provider = "claude-code-acp"` (or `"codex-acp"`), and set `LIBREFANG_ACP_CWD` to the directory the agent should work in.

These providers are not yet in the model catalog (the provider TOMLs live in `librefang/librefang-registry`), so configure them by provider id.

**Configuration:**

| Setting | Effect |
|---|---|
| `base_url` (or `[provider_urls] claude-code-acp = "/path/to/adapter"`) | Adapter executable. Wins over the env var below; also used by the availability probe. |
| `LIBREFANG_CLAUDE_ACP_PATH` / `LIBREFANG_CODEX_ACP_PATH` | Adapter executable when no config value is set. Default `claude-agent-acp` / `codex-acp` on PATH. |
| `LIBREFANG_CLAUDE_ACP_ARGS` / `LIBREFANG_CODEX_ACP_ARGS` | Extra adapter arguments, whitespace-separated (no shell). |
| `LIBREFANG_ACP_CWD` | Working directory for the adapter process and `session/new`. It must exist. **Unset: a fresh, empty scratch directory per turn, removed afterwards** (never the daemon's directory). |
| `LIBREFANG_ACP_PERMISSION_POLICY` | How `session/request_permission` is answered: `deny-all` (**default**), `allow-all`, or `allow:<kind>,<kind>` using ACP tool kinds (`read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode`, `other`). Every decision is logged at `info`. |
| `LIBREFANG_ACP_SESSION_MODE` | ACP session mode enforced right after `session/new` with `session/set_mode`. Default `default` for Claude; none for Codex. Empty keeps the agent's own mode. If the agent offers modes but not this one, the turn fails. |

**What the permission policy does and does not cover.** The policy answers only the permission requests the adapter actually sends. Claude Code decides some tool calls itself before asking: its permission mode and the allow rules in your Claude settings apply first. The driver therefore also:
- sends `_meta.claudeCode.options.allowDangerouslySkipPermissions = false` in `session/new`, which turns bypass off for the session in `claude-agent-acp` (0.84.0 `dist/acp-agent.js:6486-6488`; a `bypassPermissions` default then falls back to `default`);
- switches the session to the `default` mode (`session/set_mode`), so a `defaultMode` such as `acceptEdits` or `dontAsk` in your Claude settings does not apply;
- keeps any variable containing `DANGEROUSLY`, `SKIP_PERMISSIONS` or `BYPASS_PERMISSIONS`, and `IS_SANDBOX`, out of the adapter's environment, and never passes a skip-permissions flag;
- runs in a scratch directory by default, so no project's `.claude/settings.json` allow rules are picked up.

Allow rules in your **user** Claude settings (`~/.claude/settings.json` `permissions.allow`) still apply and are never seen by the policy. With `allow:<kind>`, the kind is the one the agent reports; a mislabelled call is judged by its label. For Codex, no session mode is enforced and `codex-acp`'s own approval behaviour has not been verified, so treat `deny-all` as covering only what it asks about.

**Environment.** The adapter starts from an empty environment plus an allowlist: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `TERM`, `LANG`, `LANGUAGE`, `LC_*`, `TZ`, `XDG_*_HOME` / `XDG_RUNTIME_DIR`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, the `HTTP(S)_PROXY` / `NO_PROXY` / `ALL_PROXY` variables, the Windows process basics, and the adapter's own prefixes: `CLAUDE_*` and `ANTHROPIC_*` for Claude (including `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_EXECUTABLE`), `OPENAI_*` and `CODEX_*` for Codex (including `OPENAI_BASE_URL`). Everything else is dropped, for example `AWS_SECRET_ACCESS_KEY`, `GITHUB_TOKEN`, other providers' keys and any unlisted `*_API_KEY`. Variables under the allowed prefixes pass even when they hold secrets, because that is how the CLI authenticates to a gateway. When a Claude subscription login exists, `ANTHROPIC_API_KEY` is also dropped so the login wins (same rule as the `claude-code` driver).

**Model gateway (Claude).** When `ANTHROPIC_BASE_URL` is set together with a credential (`ANTHROPIC_CUSTOM_HEADERS`, `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY`), the driver tells `claude-agent-acp` about the gateway over ACP instead of relying on the environment alone. It advertises `clientCapabilities.auth._meta.gateway`, and if the adapter offers the `gateway` auth method it calls `authenticate` with the base URL and the headers before `session/new`. Headers come from `ANTHROPIC_CUSTOM_HEADERS` (newline-separated `Name: Value`); `ANTHROPIC_AUTH_TOKEN` becomes `Authorization: Bearer …` and `ANTHROPIC_API_KEY` becomes `x-api-key` unless a custom header already sets them. On this route the adapter sets its own placeholder token for the CLI, so no Claude login is needed. Logs show the gateway URL and header names only, never header values. If the adapter does not offer the method, the driver logs a warning and falls back to the environment.

**Notes:** The MCP bridge headers (`X-API-Key`, agent identity) are passed to the agent in `session/new`, as the `claude-code` driver passes them in `--mcp-config`; the agent can read them. The adapter runs in its own process group. If the caller stops reading the stream, the driver sends `session/cancel` and waits 5 s; after that, and on timeout (no `session/cancel` is sent then), the whole group is killed with SIGKILL. A `claude-code-acp/<model>` model id sets `ANTHROPIC_MODEL` for the Claude adapter; bare `claude-code-acp` leaves model choice to the CLI.
